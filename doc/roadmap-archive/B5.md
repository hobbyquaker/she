# B5 — she.mqtt.age() intermittently returns NaN ✅ fixed
*Archived roadmap item — Bugs. Open items: [../../ROADMAP.md](../../ROADMAP.md) · Index: [README.md](README.md)*

**Reported (08/2026).** `she.mqtt.age()` sometimes returned `NaN` for a sensor topic, then worked again after a new reading arrived. Initially suspected to only work for payloads carrying their own `ts` attribute — actually a state-store bug.

**Root cause.** `age()` reads the state's `lc` (last change) timestamp. In the MQTT message handler (`src/index.js`), the freshly parsed state object *replaces* the stored one, and `lc` was only assigned when the value **changed** — on a repeated identical value the new state carried no `lc` and the previous one was silently discarded. Sequence: first message → `lc` set → `age()` works; same value again (typical for sensors re-reporting) → `lc` lost → `NaN`; changed value → works again. The variable branch (`var/set`) had the correct carry-over all along; the generic branch didn't.

**Fix.** The handler now resolves `lc` explicitly when the payload doesn't provide one: value changed → `lc = ts`; unchanged → previous `lc` carried over (falling back to `ts` when there is none). Payload-provided `lc` (mqtt-smarthome `{val, ts, lc}` states) keeps precedence.

**Docs** (`doc/sandbox-api.md`, `she.mqtt.age`): clarified that payloads need no own timestamps (she stamps arrival time), that `age()` measures the last *change*, and that "seconds since the last *message*" is available via `she.mqtt.getProp(topic, 'ts')`.

**Test:** integration — publish the same value twice, then assert a script's `she.mqtt.age()` returns a finite number (`test/testscripts/test-age.js` + `integration.test.js`).
