# S1 — Async callback safety: proper per-dispatch Promise wrapping ✅ implemented
*Archived roadmap item — Script Engine. Open items: [../../ROADMAP.md](../../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Implemented.** Trigger (08/2026): a script's stack-overflow error (`Maximum call stack size exceeded` in an async callback) appeared only in the Logs tab via the global `unhandledRejection` handler — unlabeled, so the Scripts tab log panel (which routes lines by the script-label prefix) could not show it.

**What shipped — cheaper than planned:** instead of touching ~6 dispatch sites, the wrapping lives in the single choke point `_dispatch(label, fn)` in `src/index.js`, which every user-callback dispatch already flows through (MQTT subscriptions, var subscriptions, schedules, sun events, timers, MQTT connect/disconnect events). When a callback returns a thenable, a rejection is caught and logged as `<script-label> async callback error: <stack>` — attributed, and therefore also routed into the script's log panel. Additionally:

- the retained-replay immediate callback invocations in `she.mqttsub` now go through `_dispatch` too (they called the callback directly);
- `she.matter.sub` callbacks are wrapped in `matter-sandbox.js` (sync + async) and log via `she.error` — labeled, panel-routed;
- the global `unhandledRejection` handler stays as a last resort for promises detached from any dispatch.

**Known gap (accepted):** stdlib target-callbacks invoked *inside* covered combiner callbacks (`or`/`and`/… with a callback target) don't get their own async wrapping — their rejections still fall to the global handler. Rare pattern; revisit if it bites.

**Test:** integration — a script with `she.mqtt.sub(..., async () => { throw ... })` produces the labeled `async callback error` line (`test/testscripts/test-async-error.js`).
