# M10 — Home Assistant discovery cleanup: delete orphaned device announcements ✅ implemented
*Archived roadmap item — MQTT, Matter & Broker. Open items: [../../ROADMAP.md](../../ROADMAP.md) · Index: [README.md](README.md)*

**✅ Implemented (2026-08-22).** Variant 1 from the plan, with the duplicate detection folded into the device table and the "also clear state topics" checkbox (default on) in the confirm modal.

What shipped:

- `src/lib/ha-discovery.js` — pure analysis over the state store: parses `<prefix>/<component>/[<node_id>/]<object_id>/config` and the device-level `<prefix>/device/<id>/config` (`cmps`) format, expands HA abbreviations and the `~` base topic, groups entities by `device.identifiers` (fallbacks: device name → node_id → component/object_id), derives per-device `statePrefixes` / `stateTopics`, and flags `orphaned` and `duplicate`.
- `src/web/mqtt-api.js` — `GET /she/mqtt/ha-discovery?prefix=` and `DELETE /she/mqtt/ha-discovery { topics }` (empty retained publish per topic, wildcards rejected, per-topic errors reported). Documented in `doc/http-api.md`.
- `web/src/pages/mqtt/HaDiscovery.svelte` — new view reachable through a *Topics / HA Discovery* switcher in the MQTT page toolbar: device table (name, identifiers, model, entity count, topic prefix, last seen, status badges), filter, per-device checkboxes with *Select orphaned*, expandable entity rows with per-announcement *Clear*, and the confirm modal listing exactly which config topics and (when the checkbox is on) which state topics will be wiped.
- `test/unit/ha-discovery.test.js` — 14 tests covering parsing, grouping, prefix derivation, shared-topic protection, the device-level format and both routes.

Decisions / deviations from the plan:

- **Availability topics are treated separately.** Only `state_topic` / `command_topic` / other `*_topic` keys derive a device's prefix and decide liveness; `availability` topics are often shared bridge topics (`zigbee2mqtt/bridge/state`) and must never end up in the wipe list. They are cleared only when they sit below a prefix derived from the device's own state topics.
- **Prefix derivation** uses the parent path of each own state/command topic instead of a single longest common prefix, so split layouts like tasmota's `tele/x`, `cmnd/x`, `stat/x` are all covered. A prefix (or any ancestor) claimed by more than one device is dropped; prefixes need at least two segments; the discovery prefix itself is never expanded.
- *Orphaned* means "none of the device's own state/command topics exist" — a stale device whose old state topics are themselves still retained is not orphaned, which is why the *duplicate* badge and the *last seen* column are shown alongside it.
- The discovery prefix is an input field in the view (default `homeassistant`) rather than a config option.

Original item text:

**Decision:** implement variant 1 (dedicated sub-tab) with the duplicate detection of variant 3 folded into the *orphaned* heuristic. Variant 2 is not planned.

**Problem.** After changing the MQTT prefix of a `*2mqtt` bridge (zigbee2mqtt, tasmota, …) the old Home Assistant autodiscovery announcements stay as retained messages under `homeassistant/<component>/<node_id>/<object_id>/config`, so every device shows up twice in HA. The announcements of one physical device are scattered across many topics in different `<component>` subtrees (`sensor/…`, `switch/…`, `binary_sensor/…`, `light/…`), so there is no single subtree to "Clear retained" recursively — the existing per-topic clear in the MQTT page doesn't help. The grouping key lives *inside the payloads*: `device.identifiers` (and `device.name`), plus `state_topic` / `command_topic` / `availability[].topic` which reveal the stale prefix.

**Backend.** she already holds every retained message in its state store, so no broker-side scan is needed. A `GET /she/mqtt/ha-discovery` endpoint parses all retained topics matching `<discoveryPrefix>/+/+/config` and `<discoveryPrefix>/+/+/+/config` (discovery prefix configurable, default `homeassistant`), groups entities by `device.identifiers[0]` (fallback: `device.name`, then node_id) and returns per device: identifiers, name, manufacturer/model, number of entities, the set of distinct state/command topic prefixes, and whether any referenced `state_topic`/`availability` topic currently exists in the state store (→ "orphaned" heuristic). `DELETE /she/mqtt/ha-discovery` takes a list of config topics and publishes empty retained payloads (reuse the existing clear-retained path). Also handles the device-level discovery format (HA 2024.4+: a single `device/<id>/config` payload with a `cmps` map) as one device.

**UI variants.**

1. **Dedicated "HA Discovery" sub-tab on the MQTT page** (recommended). A table grouped by device: name, identifiers, model, entity count, "topic prefix(es)" column, and an *orphaned* badge when none of the referenced state topics exist / no availability message is present. Checkbox per device, "select all orphaned" shortcut, a single **Delete selected** button that lists the exact config topics in a confirm modal (expandable, so users see what is going to be wiped) and then clears them. Expanding a device row shows its entities (component, object_id, config topic, state_topic) with per-entity clear. Search/filter by name, identifier or topic prefix. This is the cleanest fit because the mental model is *devices*, not topics.

2. **Payload-aware filter in the existing topic tree.** Add a "group by payload field" mode to the MQTT page's tree filter: `homeassistant/# group:device.identifiers`. The tree then shows virtual nodes per device containing the matching config topics, and the existing "Clear retained (recursive)" works on the virtual node. Less UI to build, reuses the tree, but the grouping syntax is obscure and "orphaned" detection has no natural home.

3. **Diff-style "duplicate devices" wizard.** Detect pairs of devices with the same `device.identifiers` or same `name`/`model` but different topic prefixes, show them side by side (old prefix vs new prefix, live vs stale), and offer "remove the stale one". Directly addresses the prefix-change use case but misses devices that simply went away.

**Also clear leftover state topics.** The confirm modal has a checkbox *"Also clear this device's state and availability topics"*, **enabled by default**. The backend derives the device's topic prefix from the longest common prefix of its `state_topic` / `command_topic` / `availability[].topic` values (e.g. `zigbee2mqtt-old/kitchen_light`) and clears every retained topic under `<prefix>/#` in the same action. The modal lists those topics too (collapsed, with a count) so the user sees exactly what gets wiped; if no common prefix can be derived, the checkbox is disabled with a hint. Guard: never expand a prefix that is shorter than two segments, and never touch the discovery prefix itself.

**Later.** Once more HA-related features exist (e.g. she publishing its own discovery announcements), this may move to an "Integrations → Home Assistant" page.
